### 核心内容
作者用 AI 辅助、基于 Go 技术栈 mygo 开发了一款开源 Git 可视化客户端 Banyan，直接调用本机 git，因此现有配置、hooks 和凭据都能照常生效。项目已在 GitHub 开源，release 页面提供下载。

### 关键要点
- **日志**：分支树与彩色提交图，可按文本、分支、作者、日期、路径筛选（由 git 执行筛选，不受已加载数量限制），⌘G 可跳转到哈希、分支或标签，支持对单个提交的部分文件做 cherry-pick / revert。
- **改写历史**：右键编辑提交信息、fixup、squash、drop、撤销提交，从任意提交开始交互式变基；默认保护 main / master，不会被强推。
- **提交**：支持按文件、按 hunk、按行提交，提供 Changelists、Shelf、GPG / SSH 签名。
- **冲突处理**：三栏合并工具，可自动合并的部分先合好，每处冲突可选我方 / 对方 / 两者 / 手写，并支持撤销；终端里发起的 merge 也能识别。
- **其他**：多仓库标签页、工作树与子模块、文件历史与 blame、显示每条 git 命令的控制台、Find Action 与自定义快捷键。

### 评论补充
作者说明技术栈为 [mygo](https://github.com/egoist/mygo)，从 rust + GPUI 改用 Go 的原因是包体积更小、内存占用更低，且 GPUI 的虚拟滚动更卡。软件有中文界面，操作接近 JetBrains 系。评论提到 [rebased](https://github.com/detachhead/rebased) 和 [SourceGit](https://github.com/sourcegit-scm/sourcegit) 等同类工具；也有人询问是否支持 AI 写 commit message、Excel 浏览，均未确认。

<span class="topic-title">DeepSeek 写代码的用法：做好规划与 SPEC，避免许愿式编程</span>
</summary>

<div class="topic-content" markdown="1">

<div class="topic-article" markdown="1">

### 核心内容
楼主用 DeepSeek 翻译 9 种语言的项目文件，消耗了 4000 多万 token，因此质疑其性价比。评论区的共识是：DeepSeek 不适合“许愿式编程”，它更像一个执行者，需要先由人或其他模型把方案规划清楚，再交给它执行。

### 关键要点
- **先规划再执行**：用其他模型（如 Gemini、sol）做深度规划，拆成里程碑、数据字典、详细方案和单元测试，再让 DeepSeek 按步骤执行。
- **明确技术方案**：直接告诉它用什么方案、要达到什么效果，效果“几乎不输 gpt6-sol”；只说想要什么，结果容易偏离预期。
- **控制推理等级**：用 high/default 而非 max，max 在网络不佳时可能更慢；有回复建议用 4.1 flash 而非 max。
- **省 token**：命中缓存很关键，缓存不中等于白花钱；晚上和周末使用更省；有回复提到用 omp 比较省 token。
- **定期回归测试**：不要一直写下去，否则后期 debug 会失控。

### 评论补充
有用户指出官方渠道较贵，可考虑其他渠道或 Codebuddy 薅羊毛，但也有人担心中转站注水严重。另有用户对比称，DeepSeek 擅长“指哪打哪”和小范围边界扩展，但缺乏整体业务逻辑判断，容易按下葫芦浮起瓢；Gemini 在财务逻辑等整体一致性上更强。

- **由 Herdr 决定显示**：App 不另做一套 UI，Herdr 里配置的 group 样式、布局、状态栏（如 Codex 每周用量）会同步到手机；App 自身快捷键可自由配置，方便触屏。
- **内置 code-server**：针对 Fold 折叠屏，展开后可查看和修改代码，支持文件上传、图片上传与 Diff 查看，便于与 AI Coding Agent 协作。
- **本地 Arch Linux 环境**：可在其中登录 AI Agent，用自然语言让 Agent 修改 App 设置，例如增加单手快捷键或调整折叠屏布局。
- **其他**：原生 Android、安装包尽量小巧，支持 SSH/Mosh，推荐搭配 Tailscale 连接主机；无订阅。
- 项目主页 https://yanjiyu.com/zh/terminal-spike/ ，GitHub https://github.com/Anderbone/terminal-spike 。

### 核心内容
腾讯开源的 DSpine 是推测解码推理加速方案，并非新模型：通过多层并行预测、逐层传递前一位置的预测信息，提高草稿 Token 接受率，减少解码轮次。主帖给出官方 Apple Silicon 数据：M4 Pro、64GB、Qwen3-8B BF16、T=0 单流 MLX 下，普通 mlx-lm 为 15.37 tok/s，DFlash 为 29.81 tok/s，DSpine 为 38.52 tok/s，约为基线 2.5 倍；SGLang-MLX 单并发贪心解码下为 60.46 tok/s，对照 14.77 tok/s。

### 关键要点
- Qwen3.8-27B 的 791.30 tok/s 是 SGLang+CUDA、8 并发、xhigh、开启 Prefix Cache 的 Agent 回放总吞吐，约为普通解码 3.19 倍，比 DFlash2 高约 11%，**不是单用户速度，也不是 Mac 成绩**。
- Mac 侧公开 MLX 实现主要覆盖 Qwen3-8B 这类全注意力模型；27B 高性能路线依赖 FlashAttention 3、Triton、ReplaySSM 等 CUDA 组件，不能直接把草稿模型塞进 MLX 就复现加速。
- 作者实际场景为 M5 Pro/64GB、27B 4bit 量化、128K 上下文编程 Agent，实测约 27 tok/s，Kapitsa 快时约 35 tok/s，完整任务仍可能接近两小时。

### 评论补充
评论指出需验证长上下文下 KV Cache 的线性边际递减是否会抵消加速收益，并认为 Metal 在矩阵算力、引擎优化优先级和统一内存与 CPU 竞争带宽上处于劣势；其优势可能在 MoE 架构。另有观点称 Qwen3.8 flash next 层深不及 27B，但 GPQA-D 可上 90+，提示知识宽度也可能影响推理深度。27B 在 MLX 上的实际适配与长上下文收益仍无实测结论。
